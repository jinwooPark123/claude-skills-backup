# Performance Analyzer

코드를 받아 성능 병목 지점을 찾고, 원인과 개선안을 담은 Markdown 보고서를 생성한다. 언어에 무관하게 동작한다.

---

## 워크플로우

### Step 1: 입력 파악

사용자가 코드 파일을 첨부하거나 코드 스니펫을 제공한다. 둘 다 없으면 분석할 코드를 요청한다.

- 파일이 여러 개면 각각 분석 후 종합
- 코드가 매우 길면 핵심 함수/모듈 위주로 분석하고 그 사실을 보고서에 명시

### Step 2: 성능 분석

아래 6가지 항목을 순서대로 검토한다. 문제가 없는 항목은 보고서에서 생략해도 된다.

1. **알고리즘 복잡도** — 중첩 루프, O(n²) 이상의 탐색, 정렬 중복 등
2. **반복 연산 낭비** — 루프 내 상수 계산, 캐싱 가능한 결과를 매번 재계산하는 패턴
3. **메모리 비효율** — 대용량 데이터 불필요한 복사, 참조 대신 값 전달, 메모리 누수 패턴
4. **I/O 병목** — 루프 내 파일 읽기/DB 쿼리/네트워크 호출 (N+1 문제 포함)
5. **동기/블로킹** — 비동기로 개선 가능한 순차 처리, 불필요한 대기
6. **데이터 구조 선택** — 탐색에 리스트 사용 (해시맵이 적합한 경우), 정렬된 자료구조 미활용 등

각 문제의 **심각도**를 아래 기준으로 판단한다:
- 🔴 높음: 실제 사용자 경험에 직접 영향, 즉시 수정 필요
- 🟡 중간: 데이터 규모가 커지면 문제 발생, 개선 권장
- 🟢 낮음: 미미한 개선 가능, 여유 있을 때 수정

### Step 3: 보고서 생성

아래 템플릿을 사용한다.

## 보고서 템플릿

```markdown
# 성능 분석 보고서: [파일명 또는 모듈명]

## 요약
[전체 성능 수준을 한 문장으로 평가. 예: "전반적으로 소규모 데이터에서는 문제없으나, 입력이 커질수록 O(n²) 루프로 인해 심각한 성능 저하가 예상됩니다."]

## 병목 지점 목록

| 우선순위 | 위치 | 문제 유형 | 심각도 |
|----------|------|-----------|--------|
| 1 | 파일명:라인번호 | 문제 유형 | 🔴 높음 |
| 2 | 파일명:라인번호 | 문제 유형 | 🟡 중간 |

## 상세 분석

### [병목 #1] 제목
- **위치**: `파일명:라인번호`
- **문제**: 구체적으로 어떤 코드가 문제인지 설명
- **원인**: 왜 성능 문제를 일으키는지 (복잡도, 호출 빈도 등)
- **개선안**:
  ```언어
  // 개선된 코드 예시
  ```

### [병목 #2] 제목
...

## 종합 권고사항

1. [우선순위 1] 설명
2. [우선순위 2] 설명
```

## 품질 가이드라인

- 병목이 없으면 "성능상 주요 문제가 발견되지 않았습니다"라고 명확히 기술한다
- 개선안에는 반드시 구체적인 코드 예시를 포함한다 (원칙만 나열하지 말 것)
- 심각도 판단은 실제 사용 맥락(데이터 규모, 호출 빈도)을 고려한다
- 언어별 관용적 최적화 방법을 반영한다 (예: Python의 list comprehension, JS의 Promise.all 등)
- 한국어로 작성한다 (기술 용어, 코드는 원어 사용)
